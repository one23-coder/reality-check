### 2.2 本轮新发现的 7 条（全部成立，已修）

| # | 缺陷 | 严重度 | 证据 / 修复 |
| --- | --- | --- | --- |

### 2.4 九轮新增：内核并发段（此前**从未被审过**）

对整个仓库最关键的部分做了一次专门审查：`packages/core/src/engine.ts` 的 barrier / deferred submit / retry / 观察段，以及适配器与内核契约相接的地方。7 条候选，**5 条成立并修复，2 条被我自己推翻**。

| # | 缺陷 | 严重度 | 处理 |
| --- | --- | --- | --- |
| 1 | `retry` 重放整个步骤：写操作**已派发**、只是读不回结果时，重放就是第二笔业务写入（仓库自己的 `*-cancel-waitlist` 正对 `submit` 用着 retry） | 高 | 判据从"是不是 submit"改为"**有没有派发**"：适配器报 `detail.dispatched`，内核拒绝重放已派发的写入并记 `step-retry-refused`；未派发照旧重试 |
| 2 | 内核**不校验** `runBarrier` 返回条数/顺序：少一个步骤 ⇒ 该步骤静默消失，断言在"这一步没发生"的状态上求值 | 高 | 内核自校验，不符即 blocked 并点名 |
| 3 | `when` 路径不做证据核验（正式观察路径做）：证据文件坏掉时条件仍可能判 held，**执行一步本不该发生的业务动作** | 高 | 两条路径同一口径：核验失败 ⇒ 条件无法判定 ⇒ blocked |
| 4 | 并发建页竞态：同一 actor 并发提交会各建一个 context，后者覆盖前者 ⇒ 泄漏 context + 两步跑在两页上、证据取错页 | 中 | 单次飞行；新增测试可见的 `openContextCount()` 直接钉住"一个 actor 一个 context" |
| 5 | barrier 的"同时起跑"从未被强制：真正的落库时刻交给 Playwright 的可点性检查 ⇒ **本该制造的竞态可能根本没发生**，顺序行为被读回并报成 passed | 中 | 两段式：先并行预热，再同一 tick 派发全部点击；偏移写进 `detail.fireOffsetMs`（**压小**偏移，不是证明同时落库） |
| 6 | 重试被丢弃的那次尝试，截图/DOM 已落盘却不登记 ⇒ 孤儿证据 | 低 | 丢弃前核验并登记其引用 |
| 7 | `sql-dump` 逐表 SELECT 不在同一快照；读连接无 `busy_timeout` | 低 | `BEGIN DEFERRED` + `PRAGMA busy_timeout` |

**我自己推翻的两条**（比结论更值得记）：

- **"一律禁止 `submit` + `retry`"**：这是我最初的修法，代码都写完了。但 `git log -S '"retry"'` 显示 retry 是**第三轮为 Chromium 偶发断开刻意加的缓解**（提交 `625412f`，提交信息原话 "exactly the Chromium flake found in round three"）。一律禁止会把真实抖动重新变成 blocked——用一个更坏的失败替换了一个较小的风险。改判据而不是取消能力。
- **"并发段共享计数器有并发写"**：核实后发现 `stepCounter`/`obsCounter`/`evidenceSeq` 的自增都发生在**串行**路径（deferred 的收集是同步 `for`，`Promise.all` 只包住已取好序号的提交），**未发现**并发写；文件命名前缀不同且计数单调，也**未发现**撞名覆盖。按"没有代码证据就不报"处理。

### 3.2 自检抓到的四件"我自己没想到"的事

1. **门禁抓出工具脚本漏改**：本轮新规则（应用必须声明观察器）让 `agent-loop` 关卡失败——它把 fixture 应用复制到临时目录做"外部项目"模拟，复制时只抄了 `server.js`，没抄新的声明文件。**这说明新规则在真实工具链里真的生效**，也说明只跑单测不够：门禁是独立进程 + 独立目录，是比单测更强的检查。
2. **一条修复被我自己的初判否决**：我最初打算"缺观察器声明一律 exit 64"，但回归测试显示这会把"应用入口根本不存在"这一类**环境缺失**提前变成配置错误——真实原因是"应用没搭起来"，运行本应以 `blocked`（exit 3）结束。改为分级：入口不存在 ⇒ 保持 blocked；入口存在却无声明 ⇒ 配置错误。**这是被测试逼出来的修正，不是我想出来的。**
3. **九轮里我推翻了自己已经写完的修法**：面对"retry 重放写操作"，我的第一反应是禁止 `submit` + `retry`（代码已改完）。查 `git log -S '"retry"'` 才发现它是第三轮为 Chromium 偶发断开刻意加的缓解——禁止它等于用"真实的 blocked 噪音"换掉"小概率的重复提交"。改成按**事实**判定（是否已派发），并把"不重试"这件事也写进时间线（`step-retry-refused`）。**教训：改掉一个现有行为之前，先查它为什么存在。**
4. **九轮里我还推翻了一条外部结论**："并发段共享计数器有并发写"经核实不成立（自增都在串行路径上）。三条候选里两条被推翻，说明审查结论本身也需要被审查。

## 4. 诚实边界

- **MCP 配置校验已补齐（九轮前的 1 条已知未修复缺陷已关闭）**：`checkToolsConfig()` 落到 `@rc/protocol`，CLI 与 MCP 共用；MCP 启动时配置非法直接 exit 64。
- **观察器仍不是数据库层只读连接**：强制了语句类型与表名，但连接本身未用 `readOnly` 打开——项目内曾刻意避开该标志（WAL 可见性），需实测确认后才敢开。
- **"结论不被顶掉"只做了单元级验证**：用"runsDir 指向一个文件"注入失败，断言返回 warning 而非抛异常；没有做端到端的故障注入运行。
- **并发争抢只能被"压小偏移"**：`fireOffsetMs` 证明这次是 2ms，但不能证明两笔写入真正同时落库（不是原子屏障，Playwright 每次点击仍各自复查可点性）。
- **F4（并发建页竞态）未能实测触发**：测试直接驱动不变量（一个 actor 一个 context），没有构造出真实的孤儿 context。
- **`sql-dump` 的快照改进是防御性的**：没有构造出真实的跨表矛盾快照来证明修复必要。
- **CI 托管 Runner 的运行号仍未取到**：本机没有 `gh`，`workflow_dispatch` 已就位但需要在 GitHub 侧触发；托管 Runner 依旧只有工作流定义、没有运行记录。
- **真实外部项目仍是 0**：`agent-loop` 里的"外部项目"是本仓库 fixture 的副本，不能替代真实接入。
