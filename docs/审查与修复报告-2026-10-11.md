### 2.2 本轮新发现的 7 条（全部成立，已修）

| # | 缺陷 | 严重度 | 证据 / 修复 |
| --- | --- | --- | --- |
| A | **只读是语句性质，不是表名性质**。规则 1 只校验「SQL 里出现哪些表」。口径变成应用配置后，一条写语句就能在运行中改写被测应用 | 高 | 实测 `node:sqlite`：`prepare("INSERT INTO t VALUES(1)").all()` 返回 `[]` 但行**真的写入**；多语句 `;` 亦被接受。修复：必须是单条 `SELECT`/`WITH`（去注释后判定），运行前再验一次；表/列名必须是纯标识符（它们被拼进 dump SQL） |
| B | **缺声明静默回退 fixture 预设** | 高 | 没有任何观察器声明时会拿到 booking/exam 的预设 SQL；第三方应用只要有同名表就会用 `course-1`/`holder_rc` 的口径给出**看起来完全正常的错误结论**。修复：两个参考应用各自随目录提供 `reality-check.observers.json`（测试钉住与预设一致）；入口存在却无声明 ⇒ 具名配置错误 |
| C | **CLI `--run-id` 无校验 ⇒ 破坏性路径穿越** | 高 | `export --pack` 会把 `<out>/<runId>-pack` 递归删除后重写；`--run-id ../..` 既读任意 `result.json` 又对 `--pack` 之外 `rm -rf`。MCP 侧早有守卫、CLI 侧没有。修复：`runIdProblem()`/`isSafeRunId()` 落到 `@rc/protocol` 单一来源，CLI 与 MCP 共用；测试真的建一个受害目录并断言它还在 |
| D | **呈现失败顶掉结论** | 高 | 内核已把结论写进 `result.json`，但侧车/报告写失败会抛异常 ⇒ 真实 `failed`（exit 1）在 CI 上变成 exit 70，真实回归被当成环境抖动；`readEvents` 一行 JSON 损坏也会拖垮整次运行。修复：抽出 `writeRunArtifacts()`，失败返回 warning、不抛不改退出码，CLI 与工作台都打到 stderr |
| E | **MCP 队列可能永久挂死** | 中高 | 请求串行排队；进程级 `uncaughtException` 只写日志，若它让某个 promise 永不 settle，后续请求（含 `ping`）全部挂死——服务器活着但不回答。修复：`inFlight` 追踪 + `failInFlight()` 终结在途请求 |
| F | **工作台运行不写 `cli.json` 侧车** | 中 | 工作台跑出来的 run 无法 `rerun`、`export --pack` 退化成模式规则，「三入口一致」不成立。修复：写侧车 + 回归测试（工作台跑完用 CLI `rerun` 真跑一遍） |
| G | **工作台非法 `seed`/`fault` 静默丢弃** | 中 | 用户拿到 200 + verdict，会以为那是"指定种子下的结论"，之后复跑对不上。修复：返回 400 |

### 3.2 自检抓到的两件"我自己没想到"的事

1. **门禁抓出工具脚本漏改**：本轮新规则（应用必须声明观察器）让 `agent-loop` 关卡失败——它把 fixture 应用复制到临时目录做"外部项目"模拟，复制时只抄了 `server.js`，没抄新的声明文件。**这说明新规则在真实工具链里真的生效**，也说明只跑单测不够：门禁是独立进程 + 独立目录，是比单测更强的检查。
2. **一条修复被我自己的初判否决**：我最初打算"缺观察器声明一律 exit 64"，但回归测试显示这会把"应用入口根本不存在"这一类**环境缺失**提前变成配置错误——真实原因是"应用没搭起来"，运行本应以 `blocked`（exit 3）结束。改为分级：入口不存在 ⇒ 保持 blocked；入口存在却无声明 ⇒ 配置错误。**这是被测试逼出来的修正，不是我想出来的。**

### 3.3 怎么核实别人的结论

不按对方说的"照做"，而是每条都自己拿代码证据：
- 逐条读源码确认位置与机制（不凭上一轮的记忆改代码）；
- 能实测的一律实测（`INSERT` 写入、路径穿越的受害目录、`--run-id` 的删除行为）；
- 不能实测的**明确标注为结构性推断**（沿用上一轮 spawn 失败那条的处理方式，不伪装成已验证）；
- 独立审查给出的 12 条候选，要求"文件:行号 + 代码摘录"，没有证据的直接丢弃。

## 4. 诚实边界

- **仍有 1 条已知未修复缺陷（低）**：MCP 配置不校验 `tools` 版本与 `adapter.module` 白名单（已列入下一轮）。
- **观察器仍不是数据库层只读连接**：本轮强制了语句类型与表名，但连接本身未用 `readOnly` 打开——项目内曾刻意避开该标志（WAL 可见性），需实测确认后才敢开。
- **"结论不被顶掉"只做了单元级验证**：`writeRunArtifacts` 抽出来后用"runsDir 指向一个文件"注入失败，断言返回 warning 而非抛异常；没有做端到端的故障注入运行。
- **CI 托管 Runner 的运行号仍未取到**：工作流步骤已就位（含 `workflow_dispatch`），本轮依然只有本机证据。
- **真实外部项目仍是 0**：`agent-loop` 里的"外部项目"是本仓库 fixture 的副本，不能替代真实接入。
