## 2. 逻辑层

**核心不变量**（23 条规则的骨干，全部有实现 + 测试 + 文档三处对应）：

| 语义决策 | 理由 |
| --- | --- |
| 步骤 `error` ⇒ 整轮 blocked（exit 3） | 断言在「未被触碰的状态」上求值可能**假通过**；环境失败不构成业务结论 |
| 条件步骤不成立 ⇒ `skipped`（非失败非成功） | 跳过必须可见；判定只由断言承担 |
| 条件**无法判定** ⇒ blocked | 证据不足时替用户选分支 = 伪造结论 |
| 重试只在 `error` 上触发、有界 ≤5、每次尝试入时间线 | 吸收基础设施抖动，永远洗不白业务失败 |
| 步骤证据不是断言主体 | 证明「这步发生过」≠「业务结论成立」 |
| 证据缺口必须具名（封闭集合） | 不给占位值留通过校验的空间 |
| 观察器/步骤/`when` 三路证据同一道核对闸门 | 单一真相来源，防伪造引用 |
| 数据根启动前认领 + 台账兜底清理 | §10 数据隔离在产品路径真实执行 |
| 脱敏导出宁拒产不漏检 | 反扫失败删整包；二进制默认排除不假装脱敏 |

**逻辑边界（如实）**：`retry` 不适用于 barrier 组；`when` = 单观察器 + 单比较，无组合表达式与循环体（列为 1.2 提案）；`inconclusive(2)` 与 `failed(1)` 的区分依赖证据完整性而非失败程度。

### 5.3 2026-10-11 九轮增补：内核并发段（此前从未被审过）

前两轮的审查都绕开了 `packages/core/src/engine.ts`——最容易出问题、也最该被审的一块。九轮专门审它（barrier / deferred submit / retry / 观察段），**5 条成立并修复，2 条被推翻**（方案附录 A.15）。

| # | 缺陷 | 严重度 | 修复 |
| --- | --- | --- | --- |
| 1 | `retry` 重放整个步骤 ⇒ 已派发的写操作会被**再写一笔**（仓库自己的 cancel 场景正对 `submit` 用着 retry） | 高 | 判据改为**有没有派发**：适配器报 `detail.dispatched`，内核拒绝重放已派发的写入并记 `step-retry-refused`（未派发照旧重试，保住第三轮的抖动缓解） |
| 2 | 内核不校验 `runBarrier` 的返回条数/顺序 ⇒ 少一个步骤就静默消失，断言在"这一步没发生"的状态上求值 | 高 | 内核自校验，不符即 blocked 并点名 |
| 3 | `when` 条件路径不做证据核验 ⇒ 证据坏掉时条件仍可能判 held 并**执行一步本不该发生的动作** | 高 | 与断言同一口径：核验失败 ⇒ 条件无法判定 ⇒ blocked |
| 4 | 并发建页竞态 ⇒ 泄漏 context + 两步跑在两页上、证据取错页 | 中 | 单次飞行；`openContextCount()` 直接钉住"一个 actor 一个 context" |
| 5 | barrier 的"同时起跑"从未被强制 ⇒ **本该制造的竞态可能没发生**，却被读成 passed | 中 | 先并行预热、再同一 tick 派发；`detail.fireOffsetMs` 让偏移可查（**压小**而非证明同时） |
| 6 | 重试被丢弃的尝试其证据成孤儿 | 低 | 丢弃前登记引用 |
| 7 | `sql-dump` 跨表非同一快照；读连接无 `busy_timeout` | 低 | `BEGIN DEFERRED` + `PRAGMA busy_timeout` |

**方法论**：这一轮**推翻了自己已经写完的一条修法**（一律禁止 `submit`+`retry`）——查 `git log` 后确认 retry 是第三轮为 Chromium 偶发断开刻意加的缓解，一律禁止等于用真实噪音换掉小概率风险。改判据而不是取消能力。另有一条外部结论（"并发段共享计数器有并发写"）经核实不成立。

**风险表更新**：`when` 与并发组这两条新的高危面**已关闭**；新增一条低危诚实边界——barrier 的争抢只是"压小偏移"，**无法证明两笔写入真的同时落库**（`fireOffsetMs` 可查）。
