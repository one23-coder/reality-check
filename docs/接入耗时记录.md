## 每处阻碍记录

1. **exams 侧候补队列观察器缺失**：适配器清单里的 `waitlist-head` / `waitlist-order` SQL 硬编码 `course_id = 'course-1'`，而 exam 库 `waitlist` 表列为 `exam_id`——这两个观察器对 exam-1 必然 SQL 报错，不能声明为场景观察器（`observe()` 走清单 SQL，场景里写对的 SQL 也不被采用）。exams 侧可用的清单观察器只有 `seat-count`、`seats-left`。
2. **协议 1.0 无字符串断言**：`AssertOp` 仅有 `eq/ne/gt/gte/lt/lte/countEq` 且断言主体必须为数值列，没有 `eqStr`。因此 `waitlist-declared-order` 无法用「队首账号 = 声明账号」表达，只能仿照 booking-cancel-waitlist 的先例以数值表达（递补后 `seats-left` 回到 0），队列顺序本体不作断言主体。已在场景 `description` 与规则描述中如实记录该局限及对 `waitlist-order-wrong` 故障甄别的影响（单元素队列上与正确实现状态同构）。
3. **观察器口径命名**：booking 用 `booking-count`/`capacity-left`/`bookings`/`courses`，exam 是 `seat-count`/`seats-left`/`reservations`/`exams`——首次写场景时需逐一对照清单，不能凭 booking 记忆复用（列名 `n`/`left` 一致，迁移成本低）。
4. **内核不传角色种子（规则 7）**：`seedRole: "holder"` 只把账号写进库并落一条初始预约，「占座意图」仍须由场景的显式 register/login/navigate/submit 步骤保证；两个 holder 占满容量的场景需要两个 `holder` 角色各走完整预约流程。
5. 无其他阻碍：app 端点为原生 POST + 绝对 URL（规则 5），`/reserve?exam=exam-1`、`/cancel?exam=exam-1` 与 booking 的 navigate/submit 步骤同构；配置文件结构与 `.reality-check.json` 完全一致，仅换 `entry` 与 `runsDir`。
